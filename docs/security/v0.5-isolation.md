# CodeGuardian v0.5 — OS Isolation, Network Containment & Security Engine

## Overview

CodeGuardian v0.5 introduces an OS-level execution isolation framework, network containment policy, resource governance, and a fail-closed Security Lifecycle State Machine.

v0.5 resolves key architectural limitations of prior releases:

1. **OS-Level Container & Process Isolation**: Execution sandboxes run in Docker containers (when available) or OS process groups / Job Objects.
2. **Network Containment**: `NetworkPolicy` allows explicit network denial (`mode: NONE`) or host/port allowlists (`ALLOWLIST`).
3. **Fail-Closed Isolation Selection**: `IsolationFactory` strictly compares required isolation strength (`policy.requiredLevel`) against guaranteed provider capabilities. If container isolation is required but Docker is unavailable, the pipeline **fails closed (`BLOCK`)** with `ISOLATION_UNSATISFIABLE`.
4. **State Machine Lifecycle Governance**: Commands progress through an explicit 12-state security lifecycle (`PROPOSED` $\rightarrow$ `PARSED` $\rightarrow$ `POLICY_CHECKED` $\rightarrow$ `CAPABILITY_GRANTED` $\rightarrow$ `ISOLATION_PREPARED` $\rightarrow$ `ISOLATION_VERIFIED` $\rightarrow$ `PROCESS_STARTED` $\rightarrow$ `PROCESS_RUNNING` $\rightarrow$ `PROCESS_TERMINATED` $\rightarrow$ `EFFECTS_VERIFIED` $\rightarrow$ `COMPLETED`).
5. **No Recursive Execution Loop**: `ContainerIsolationProvider` launches Docker containers via a dedicated, direct host CLI launcher, never recursively calling CodeGuardian's governed `execute_command` tool.

## Architecture

```text
AI Action Proposal
       ↓
CommandParser           → Parse CLI tokens, flags, operators
       ↓
CommandPolicy           → Evaluate structural rules
       ↓
ExecutableResolver      → Resolve binary path & trust level
       ↓
NpmScriptAnalyzer       → Inspect nested package.json scripts
       ↓
CapabilityManager       → Create CapabilityGrant & IsolationPolicy
       ↓
SecurityStateMachine    → Transition: PROPOSED → PARSED → POLICY_CHECKED → CAPABILITY_GRANTED
       ↓
IsolationFactory        → Match & initialize IsolationProvider (Container / ProcessGroup)
       ↓
IsolationEnvironment    → Launch execution sandbox
       ↓
SecurityStateMachine    → Transition: ISOLATION_PREPARED → ISOLATION_VERIFIED → PROCESS_STARTED
       ↓
Execution Sandbox       → Execute command with network denial, path mounts, resource caps
       ↓
EffectObserver          → Detect pre/post state & process/network diffs
       ↓
EffectFirewall          → Validate observed effects vs capability
       ↓
SecurityStateMachine    → Transition: EFFECTS_VERIFIED → (COMPLETED | VIOLATED | ROLLED_BACK)
       ↓
Rollback / EvidenceLedger → Atomic rollback on violation; append evidence hash chain
```

## Isolation Hierarchy & Level Weights

| IsolationLevel | Weight | Guaranteed Capabilities | Provider |
|----------------|--------|--------------------------|----------|
| `NONE` | 0 | Un-isolated execution | N/A |
| `PROCESS` | 1 | Process group / Job Object boundary, sanitized env, timeout | `ProcessIsolationProvider`, `HostFallbackProvider` |
| `FILESYSTEM` | 2 | Path chroot / mount restrictions | `ContainerIsolationProvider` |
| `NETWORK` | 3 | Real network namespace / interface denial (`--network none`) | `ContainerIsolationProvider` |
| `CONTAINER` | 4 | Read-only root mount, non-root user, dropped capabilities, cgroups | `ContainerIsolationProvider` |
| `FULL` | 5 | Container + strict network & resource sandbox | `ContainerIsolationProvider` |

### Strict Level Comparison Rule

`IsolationFactory.selectProvider()` evaluates:
$$\text{ISOLATION\_LEVEL\_WEIGHTS}[\text{actual}] \ge \text{ISOLATION\_LEVEL\_WEIGHTS}[\text{required}]$$

If a provider's guaranteed level is weaker than `policy.requiredLevel`, it is **strictly rejected**. For example:
- `requiredLevel = CONTAINER`, available = `PROCESS` $\rightarrow$ **`ISOLATION_UNSATISFIABLE` (`BLOCK`)**
- `requiredLevel = PROCESS`, available = `PROCESS` $\rightarrow$ **Allowed**

## New Evidence Ledger Events (v0.5)

| Event Name | Trigger |
|------------|---------|
| `ISOLATION_REQUESTED` | Isolation policy & required level calculated |
| `ISOLATION_CREATED` | Isolation environment instantiated by provider |
| `ISOLATION_VERIFIED` | Sandbox parameters verified prior to process launch |
| `ISOLATION_FAILED` | Provider unavailable or requirement unsatisfied (fails closed) |
| `NETWORK_POLICY_APPLIED` | Network mode (`NONE`, `ALLOWLIST`) configured |
| `RESOURCE_LIMIT_APPLIED` | CPU, memory, timeout, and output bounds applied |
| `SANDBOX_PROCESS_STARTED` | Process launched inside sandbox |
| `SANDBOX_PROCESS_TERMINATED` | Process execution ended inside sandbox |
| `SANDBOX_DESTROYED` | Sandbox environment torn down and cleaned up |
| `ISOLATION_VIOLATION` | Sandbox escape or policy violation detected |

## Known Platform Limitations

1. **Docker Runtime Dependency for `CONTAINER` Level**: Container isolation requires Docker CLI and daemon. If Docker is missing, `ContainerIsolationProvider.isAvailable()` returns `false`. If `CONTAINER` level was explicitly required, execution fails closed (`BLOCK`).
2. **Windows Process Group Boundaries**: Windows uses Job Objects and process tree termination (`taskkill /F /T`). Full Linux cgroups/namespaces require WSL2 or Docker Desktop on Windows hosts.
3. **Network Heuristics on Host**: Host-level process isolation uses heuristic network detection (`NetworkPolicyValidator`). Real network interface suppression (`--network none`) is enforced when executing inside container sandboxes.
